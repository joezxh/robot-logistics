## 摘要

视觉-语言-动作（Vision-Language-Action，VLA）模型标志着机器人学习领域的一次重大转变。它们以大规模数据采集和针对特定平台的微调，取代了专家策略中那些为特定任务设计的专业化架构和组件。在这一以模型和可扩展训练为核心的机器学习工作流中，传统的机器人软件框架成为瓶颈，而机器人物理仿真仅在从仿真到真机、以及从真机回到仿真的迁移上提供有限支持。

本工作中，我们通过引入 **Robot Control Stack（RCS）** 来弥合这一鸿沟。RCS 是一个精益（lean）生态系统，从设计之初就将支持大规模通用策略（generalist policies）的机器人学习研究纳入考量。

RCS 的核心是一个模块化、易扩展的分层架构。它为仿真机器人和物理机器人提供了统一的接口，方便开展 sim-to-real 迁移。尽管 RCS 占用极少、依赖项极少，但它提供了完整的功能集，使其既支持真实环境实验，也支持大规模仿真训练。

本文的贡献有两方面：

1. **架构**：我们介绍 RCS 的架构，阐述其设计原则。
2. **评估**：我们沿 VLA 与强化学习（RL）策略的开发周期，对其可用性与性能进行评估。我们的实验还对 Octo、OpenVLA 和 π₀ 在多种机器人上进行了广泛评估，并揭示了仿真数据如何提升真实环境下的策略性能。代码、数据集与演示视频均已公开（项目主页）。

## I 引言

机器学习在机器人研究中的作用越来越重要。虽然机器人研究早期就采用了来自人工智能的方法 [18]，但近期基础模型（foundation models）的进展正在挑战传统机器人学习方法，并开辟出新的机遇。用于机器人操作的视觉-语言-动作（VLA）模型将感知、动作生成等多个组件融合在一起，构成端到端策略，使其能够跨任务、跨机器人、跨环境泛化 [8, 11, 2]。而只有依靠全社区的数据收集工作 [19, 10, 28]，才使得规模化训练成为可能。

这种工作流与传统的机器人实验有着根本的不同。在传统机器人实验中，机器学习通常只是整个方法的一小部分，训练得到的模型只是某个预定义系统架构中的一环。许多机器人软件包就是基于这一原则设计的 [15, 20]，因此并不适合以机器学习为中心的研究——在这些研究中，机器人硬件平台是训练与推理循环的一部分，而不是凌驾于循环之上的"前置装置"。许多面向机器人学习的仿真器解决了这一问题，并在大规模并行训练中表现良好，但它们缺乏核心的机器人学功能，也只提供有限的物理机器人控制能力 [29, 31, 23]。结果是：VLA 与机器人学习的研究，对每个新平台、新模型和新任务都仍需做定制。一个能够灵活适应每套机器人平台各自的特性、良好集成社区标准以促进模型与数据共享、并与最前沿机器学习工具和工作流无缝衔接，从而支持新模型与方法的研究与开发的软件生态，依然是缺失的。

本文中，我们提出 **Robot Control Stack（RCS）**——一套从设计之初就为 VLA 研究量身打造的机器人学习库与工具集。RCS 基于一个轻量级的分层架构，可以在不同的抽象层级方便地扩展（见图 1）。其核心是以 C++ 接口来支持低层 API，并统一管理集成 MuJoCo 物理仿真 [25] 与真实机器人硬件之间的控制。配套的、基于 Gymnasium [26] 的 Python API，配合模块化的环境包装器（environment wrapper），使高层应用的实现变得便捷——包括数据采集、已训练策略部署、传统任务与运动规划；RCS 与 MuJoCo 的紧密集成还提供了无缝的 sim-to-real 与 real-to-sim 双向支持。简而言之，RCS 是一套精益的机器人学习生态系统，**旨在去适配你的应用，而非让你反过来适配它**。

综上，本文做出如下贡献：

1. 介绍 RCS，展示其基于环境包装器的架构如何在不同的抽象层级添加新特性，并同时支持基于 Python 与基于 C++ 的机器人软件；
2. 在跨机器人形态（cross-embodiment）、仿真与真实环境下的训练数据采集，以及 VLA 与 RL 智能体的训练与评估等常见用例上评估 RCS；
3. 为 Octo [8]、OpenVLA [11] 和 π₀ [2] 在一系列不同机器人上的一个可复现抓取任务上给出广泛的实验结果；
4. 重点展示合成数据如何与真实数据混合能够显著提升 π₀ 在真实环境下的策略性能 [2]。

**图 1：RCS 的分层架构。最上层的应用通过 Gymnasium 化的 Python API 访问机器人、传感器和执行器，从而方便地在硬件和 MuJoCo 仿真之间切换。下层暴露 C++ API 用于性能关键的功能，使 RCS 同时适用于端到端策略学习和低层控制。**

## II 相关工作

机器人领域的软件包对加速开发、促进科研可复现性一直发挥重要作用。许多库提供机器人核心功能 [22, 5] 与特定领域的算法集 [24, 4]。

由于典型的机器人平台涉及很多组件，组装一个集成系统很快就会变得复杂。这催生了 Yarp [15] 和 ROS [20] 等机器人中间件的开发。前者专注于通信，而 ROS 已发展为在研究与工业界被广泛使用的大型生态。尽管 ROS 灵活到几乎可以支持任何架构，但搭建一个稳健、单一用途的栈（stack）需要理解其复杂的底层。以机器学习为驱动的应用必须仔细协调硬件与软件组件，包括仿真与真实环境。这就是为什么面向任务优化的架构通常比通用而全能的 ROS 架构开销更低、更易用。

Ark [6] 实现了与 ROS 类似的架构，但加入了关键的机器学习特性，例如基于 Gymnasium 的 Python API [26]、原生 sim-to-real 支持、数据采集工具。但它也缺乏对并行化和强化学习（RL）的支持。RCS 与基于中间件的系统不同——它默认不是分布式的，这使得它在需要时可以同步执行、容易并行化、并同时支持在线和离线学习。不过，单个组件依然可以通过远程过程调用（RPC）分布式部署。

在面向机器人操作的机器学习领域，实验平台通常比较简单，仅由一个机械臂、一个夹爪和若干摄像机组成。一些专门为流行的 Franka Emika Panda 机器人设计的库提供了基本的机器人控制功能，没有大型框架的额外开销。panda-py [7] 与 frankx [1] 提供了侧重于运动生成的 Python 基础接口；Deoxys [30] 与 Polymetis [14] 的重点在于自定义力矩控制器。后两者也与选定的仿真器对接，其中 Deoxys 与 robosuite [31] 集成。RCS 同样对接仿真机器人与物理机器人，但它并不局限于单一机器人型号。此外，它还支持让物理机器人与基于 MuJoCo 的仿真 [25] 并行运行，从而构成"数字孪生"。

与本文工作最相关的是 Isaac Lab [16] 与 LeRobot [3]。两者都是专为机器人学习设计的，并深度集成于各自的生态系统中。Isaac Lab 提供了覆盖广泛的应用与算法的全面特性集。然而虽然它对 ROS 有支持，却没有提供在仿真与硬件之间无缝切换的能力。LeRobot 则不提供低层 API 支持，限制了硬件集成的可选方案，并且缺少核心的机器人学功能，例如逆运动学（IK）与路径规划。

## III 方法

RCS 围绕"环境包装器（environment wrapper）"概念来设计。一个环境包装器是一个元组 `W = ⟨ f : S → S′ , g : A′ → A , P′ , R′ ⟩`，其中 `f` 和 `g` 是将马尔可夫决策过程（MDP）的状态与动作做变换的映射；`P′` 和 `R′` 是可选的新状态转移概率函数和奖励函数。包装器 `W` 可对 MDP `M = ⟨S, A, P, R⟩` 进行**应用**，得到新的 MDP `M′ = ⟨ S′ , A′ , P′ , R′ ⟩`。我们记为 `M′ = W ⊳ M`，并称"W 包装了 M"。注意 `f` 和 `g` 的方向性差异：`f` 将被包装的 MDP `M` 中的状态变换为新 MDP `M′` 中的状态；而 `g` 将新 MDP `M′` 中的动作变换为被包装 MDP `M` 中的动作。它们也可以实现为恒等函数 `f_I`、`g_I`，使得 `S′_t = S_t = f_I(S_t)`、`A′_t = A_t = g_I(A_t)`。

上述形式化可以扩展到部分可观测马尔可夫决策过程（POMDP），以更贴近 Gymnasium 环境 [26] 的实际 API。`f` 和 `g` 的方向性保持不变，我们可以复用 `⊳` 关系来表示对 POMDP 的包装。

### III-A 库架构

图 2 显示了 RCS 的架构。其最底层是一个 C++ 接口，以抽象方式定义了控制机器人所需的全部函数。该接口具有 Python 绑定，因此新机器人的支持可以在 C++ 和 Python 任一语言中实现。基础环境通过配置控制类型（如笛卡尔或关节控制、同步或异步动作等）来实例化，并调用同一套接口函数。这一设计与具体实现无关，可与任何机器人、甚至任何 MuJoCo 场景配合工作。

每个场景（scene）由 `n` 个包装器按顺序组成，每个包装器都可以变更环境的动作和/或观测空间。例如，一个夹爪包装器会同时为动作和观测空间添加一个维度；一个相机包装器会向观测空间添加一帧图像。形式上，在每个时间步，智能体（策略或遥操作员）向被包装的 MDP `M^(n) = W^(n) ⊳ … ⊳ W^(1) ⊳ M` 发出一个动作 `A_t = A_t^(n)`，然后该动作沿包装器的动作变换链传播：`A_t^(0) = g^(1)( … g^(n)( A_t^(n) ) … )`。`A_t^(0)` 被传给基础 MDP——即实现机器人的接口——产生一个观测状态 `S_t^(0)`。类似地，观测变换链更新状态：`S_t^(n) = f^(n)( … f^(1)( S_t^(0) ) … )`，并返回给智能体；该过程持续直至到达终止状态。恒等包装器（identity wrappers）可用于记录轨迹数据，或在机器人与远程机器之间通过网络流式传输动作与观测。

#### III-A1 硬件抽象

原则上，添加新硬件只需编写一个新的包装器。然而由于许多硬件设备具有相似的输出，并需要相似的工具代码——例如每个相机都输出 RGB 图像且都需要轮询线程——RCS 为常见传感器与执行器定义了接口与开箱即用的包装器，包括：实现相机轮询的包装器（针对遵循相机接口的一组相机）以及用于夹爪或机器人手等末端执行器的包装器。

默认情况下，Gymnasium 环境是同步的，因为智能体的动作 `A_t` 需要被环境的返回状态 `S_(t+1)` 完全反映。因此 RCS 默认在仿真与硬件上都同步运行：仅当所定义的状态已经被达到后才返回一个动作。但这并不妨碍将 RCS 配置为异步执行，使 step 函数立即返回——例如在遥操作场景中。无论如何，基于 step 的设计都确保来自不同传感器的观测在时间上是同步的。

#### III-A2 仿真

RCS 借助 MuJoCo 物理仿真，并针对机器人学用例扩展了其 API，同时保留 MuJoCo 的核心数据结构对外暴露，以保持灵活性。其目标是提供仿真场景的面向对象视图，便于快速实验、便于添加新的仿真机器人、执行器和传感器。

为支持同步操作与中断，RCS 在 MuJoCo 的 step 函数之上实现了一套回调（callback）机制。例如，在包含机械臂的场景中，一个同步的高层方法"闭合夹爪"需要夹爪在达到闭合状态时通知仿真。仿真应继续步进，直到所有实体收敛到最终状态，例如直到机械臂到达其目标位置。另一些情况下，仿真应被直接中断——例如检测到碰撞时。该回调机制使得各个仿真实例能够实现这样的高层功能，镜像在真实硬件上运行的传统机器人软件。

#### III-A3 机器人学工具包

RCS 还集成了成熟的工具与库，以提供核心的机器人学功能。我们使用 Pinocchio [4] 作为运动学的后端。由于 Pinocchio 与各种机器人描述文件格式广泛兼容、且计算开销低，其函数已被集成，从而在仿真和真实环境中跨机器人无缝工作。机器人模型基于 MuJoCo 的 MJCF 描述，而后者可被 Pinocchio 读取。由于 RCS 自带一份所支持机器人的 MuJoCo 基础场景，因此开箱即用地提供了基于 Pinocchio 的 IK 求解器。还集成了 OMPL [24]，以支持基本的运动规划，并在自动化数据采集中提供更多样的轨迹。

由于仿真机器人与真实机器人使用同一接口，因此很容易实现新的工具以产生协同效应——例如让一个并行的仿真实例与真实机器人实时运行相同的动作序列。除了作为原型工具外，这种能力也可用于规划场景：在执行真实动作之前先在仿真中验证。RCS 还包括相机标定接口，使得能够实现针对特定平台的自定义标定策略，例如图 3 所示的 AprilTags。

### III-B 应用与生态

应用（apps）通常是高层脚本，利用按用例与平台定制的包装器组合来控制物理或仿真机器人。App 也可以是执行只读操作的包装器，例如将场景中的信息以特定格式存储的存储包装器。大多数 app 可分为两类：生成并记录机器人行为（用于下游模仿学习），或执行一个策略用于评估。RCS 自带了多种 app，例如使用不同硬件的遥操作、OMPL 等轨迹生成器、以及策略推理引擎。

VLA 策略与其他近期的深度学习模型往往带有一组相当固定的软件依赖，这些依赖可能与目标机器人平台的控制软件依赖不兼容。为应对这一问题，RCS 提供了一个专用的应用层库，称为 **VLAgents**。VLAgents 以一个依赖极少的轻量级 Python 包实现，可以被安装到策略自身的 Python 环境中。然后，VLAgents 包被用来与策略的推理管道对接，创建一个服务端实例。这个服务端与部署在并行 RCS 环境中的 VLAgents 客户端实例通信。两实例之间的通信通过 RPC 实现——跨机器时使用 TCP，在同一台机器上则使用共享内存。该方法带来两个主要好处：(1) RPC 允许传输的数据像普通本地变量一样访问，两端形成一致的接口；(2) 在每个时间步，所有观测都已被预先对齐，因为对齐由生成数据的各层负责。VLAgents 目前已集成七种策略与三种仿真环境。

### IV-B 系统性能

早期的 VLA 架构（如 OpenVLA）以较低的推理频率运行，约 5 Hz；更新的模型（如 π₀）则可达 50 Hz。为验证 RCS 是否能满足这些性能需求，我们在图 4 所描述的三套平台下，测量了遥操作过程中在固定控制频率下的数据录制频率。所有平台基于最多两台 FR3 机械臂，并包含最多四台 RealSense 405 和 435d 相机，分辨率设置为 1280×720。其中两套平台还额外录制了两个 DIGIT 触觉传感器，分辨率 320×240。所有相机以 30 fps 运行。若录制频率更高，则采用最新可用帧。这对本体感知数据（proprioceptive data）并不需要——后者本身就是以高频可用。

图 4 显示，所有配置可达到最高 90 Hz（双相机 FR3 可达 120 Hz）。当控制频率更高时，IO 瓶颈会导致抖动，最大帧率受相机数量限制。重要的是，尽管 Gymnasium 环境是同步的，RCS 在较高频率下仍能良好伸缩，适合现代 VLA 与 RL 部署。

**图 5：复刻的仿真场景。左：FR3 的仿真场景，标定后的相机位姿以浅绿色显示。右：真实平台（上）与仿真平台（下）中腕部与侧面相机的图像对比。**

### IV-C 任务与数据集

在模仿学习中，数据集——即机器人执行某项任务的录制数据——对下游模型的性能至关重要。为了对比不同的视运动策略（即 VLA 策略），我们需要一个在基准任务上收集的数据集。该基准任务须满足：(1) 可在真实环境与仿真中执行；(2) 跨平台可复现。虽然已有满足这些要求的基准，如 FurnitureBench [9]，但它们常常包含过于复杂的任务，对能力较弱的模型并不友好，从而妨碍了模型之间的有意义的对比。为使这样的对比成为可能，我们设计了一个简单的任务—— **Pick-Cuboid（抓取长方体）**：抓取一个绿色的 3D 打印长方体，其位姿在每轮中以不同的方向随机摆放。该长方体在工作空间的一个指定区域内随机摆放，其位置和方向都使用种子以保证可复现。在仿真中，长方体位姿可直接设定；在真实环境中，我们手动放置或由机器人自身摆放。仿真与真实任务示例如图 5 所示。

在录制中，我们使用一个 recorder 包装器，从场景中获取数据，在时间上对齐观测与动作，并将数据写入一个 Parquet 文件。我们的数据均以 30 Hz 的频率录制。数据集中的观测包含完整机器人状态——包括以弧度表示的绝对关节角、机器人在基坐标系下的笛卡尔末端执行器位姿（坐标系在所有机器人间统一）、夹爪状态以及相机的 RGB 与深度图像。如果相机被标定，相机数据帧还包含内参与外参矩阵。

下面针对每个平台简短描述其数据采集过程。

#### FR3

我们在 FR3 平台上使用 HTC Vive VR 输入设备与一个操作空间控制器（operational space controller），通过遥操作录制了 143 次 Pick-Cuboid 任务演示。如前所述，我们使用机械臂自身将长方体放置到 30 cm × 40 cm 工作空间内的一个随机位置和姿态。这样我们可以在人类摆放没有主观偏差的情况下，对该区域内的立方体位置进行采样。除此之外，我们还知道立方体的位置，该信息被记录在数据集中，可用于在仿真中重放轨迹。

#### xArm7

我们使用 Meta Quest VR 控制器通过遥操作采集了 100 次演示。由于 Pick-Cuboid 任务中的长方体对 Tilburg Hand 而言太小、无法可靠抓取，我们使用了一个更适合手部大小的可变形玩具代替。我们将这个变体任务称为 **Pick-Toy**。每轮中，我们手动将物体放置在 60 cm × 30 cm 工作空间内的随机位置和方向。然后我们遥操作机器人，从初始姿态出发，触达物体、抓取并提升回初始姿态。

#### UR5e

我们使用 SpaceMouse 进行笛卡尔速度控制，对机器人进行遥操作并采集 167 次演示。每次演示中，Pick-Cuboid 中的长方体被手动放置在 50 cm × 50 cm 工作空间内的随机位置和姿态。我们遥操作机器人抓取长方体、提升并保持物体回到初始姿态。

#### SO101

我们沿用了与其他平台相同的实验流程，但使用了更小的长方体来匹配机器人尺寸，并采用 35 cm × 20 cm 的工作空间。总共使用机器人的 leader-follower 遥操作平台录制了 120 次演示。

#### 脚本化仿真 FR3

脚本化仿真回合通过一个简单的线性插值器引导机器人末端执行器到达长方体来生成，其位姿包含在 MuJoCo 数据中。由于接触仿真存在不确定性，任务不一定能成功，因此我们使用一个观察长方体高度的简单包装器来判断任务是否成功。该过程可以多线程化，在消费级 GPU 笔记本上每 20 分钟可产出约 1000 条回合，然后基于成功准则筛选。利用上述仿真环境和与真实 FR3 相同的任务配置，我们生成了 3000 条这样的回合，成功率 73%，最终得到包含 2193 条成功仿真演示的数据集。

为定性地探索真实与仿真 FR3 平台之间的差距，我们使用上面所述 FR3 演示中观察到的机器人状态，将每条回合在仿真中重放。得益于自动化的长方体摆放算法与相机标定，我们能够密切复现该场景，如图 5 所示。重放得到的数据集按上述成功准则筛选，得到 73 条成功的回合。

### IV-D VLA 实验

为了展示 RCS 如何支持并加速 VLA 研究，我们在所介绍的任务与机器人平台上评估了多种 VLA。

#### IV-D1 π₀ 在不同平台上的实验

我们在前述所有四套平台上评估 π₀。我们针对每套平台基于其各自的数据集对一个模型做微调。各模型使用各自的权重，每个实验相互独立。由于 RCS 灵活的基于包装器的架构，我们可以共享遥操作与模型执行的代码，最大限度降低硬件相关的开销。评估中，我们沿用了数据采集时的 30 Hz 控制频率，并采用动作块（action chunking），预测时域为 20 步。每个模型在 50 次真实环境回合上进行评估。所得的评估成功率如图 6 左上所示。

##### FR3

在所有硬件平台中，FR3 平台基于 π₀ 获得了最高性能。这一结果在意料之中——π₀ 的预训练数据集中有一部分就包含了 Franka 机械臂。

##### xArm7

在 xArm7 平台上，π₀ 表现良好，尽管与其他平台相比末端执行器有显著差异——这体现了它跨形态的泛化能力，包括对多指机器人手的泛化。这一性能也部分归因于多指抓取本身的鲁棒性，以及用于 Pick-Toy 任务的物体在几何与物理特性上便于抓取。由于该物体不需要像绿色长方体那样从特定角度抓取，任务也更简单。

##### UR5e

UR5e 机器人与 Robotiq 夹爪也属于 π₀ 的预训练数据集，因此其表现良好。与 FR3 性能差距的一个原因可能是 UR5e 实验中使用了更大的工作空间，使任务更难——尤其在机器人奇异点附近。此外，UR5e 实验中的长方体是手动放置的，因此存在一定的人类主观偏差。

##### SO101

相比其他机器人，π₀ 在 SO101 上的表现明显较差。我们推测原因如下：(1) 机器人更低的自由度与更小的尺寸与 π₀ 训练数据集中的平台对齐不佳；(2) 在夹爪固定指一侧抓取物体经常导致意外的碰撞，而在可动指一侧的物体较少遇到这一问题；(3) 机器人低成本组件固有的误差余量更大，例如连杆挠性与电机齿隙。

#### IV-D2 多种 VLA 在下一步预测上的对比

本实验中，我们在 FR3 平台上对比三种开源 VLA 策略——经过 FR3 数据集微调的 Octo、OpenVLA 和 π₀。这些模型代表了开源 VLA 的近期进展。由于这些模型在动作预测方面的架构有差异，我们将数据降采样到 5 Hz（OpenVLA 使用的频率），并只进行同步的下一步预测。原因是 OpenVLA 只能进行下一步预测，因此与采用动作块的模型进行对比是不公平的。此外，更高频的控制频率对下一步预测会成问题——因为模型几乎看到与之前相同的状态，会陷入小幅动作。最后，这些模型都被训练来预测精确状态，因此在同步操作下应能取得最佳结果。

我们在真实平台上的 30 次回合以及在复刻的 MuJoCo 场景中的 100 次回合上，使用同一组长方体摆放位姿评估上述模型（见图 5）。后一种评估揭示了 real-to-sim 能力，类似于 SIMPLER [13]。良好的 real-to-sim 性能不仅反映了模型的泛化能力，也是一项重要指标——若它与真实环境性能相关，则可用于训练阶段的模型设计与超参数选择。评估结果如图 6 右上所示。

Octo 和 OpenVLA 即使在这项相当简单的抓取任务上表现也较弱。这可以由它们的预训练数据集分布解释——其中只有一小部分是关于 Franka Emika Panda 机器人（FR3 的前代）的。这些模型的低成功率也与先前工作 [2] 一致。π₀ 的性能相比其 30 Hz 版本略有下降，这是符合预期的——因为其预训练数据集主要由 50 Hz 与 30 Hz 的轨迹构成。它还具备一定程度的向仿真迁移的能力，而其他两个模型都不能泛化到这个新的仿真域。

#### IV-D3 π₀ 在仿真中的评估

与 SIMPLER 的思路类似，我们在仿真中对基于 FR3 数据集微调的 π₀ 策略进行评估（real-to-sim）。不同于上一节只评估最终结果，我们在训练过程中对每一个 checkpoint 都做评估。所得的成功率曲线如图 7 左侧所示。如图所示，仿真环境的成功率给真实平台的成功率提供了一个下界，这可能源自仿真所引入的域差（domain shift）。与 SIMPLER 一致，我们的结果显示仿真与真实域之间存在松散的相关性。

#### IV-D4 π₀ 在合成数据混合下的实验

本实验中，我们基于 FR3 与脚本化仿真 FR3 数据集的真实与合成数据混合，训练 π₀。图 6 下方柱状图展示了三种训练混合：一份来自真实域的 10 个回合、一份来自仿真域的 100 个回合、以及二者结合的一份。第一个实验显示，π₀ 在小数据集条件下不能迁移到新任务与新平台。有趣的是，它仍然具备 real-to-sim 迁移能力。第二个实验的结果表明，这种能力在 sim-to-real 方向上也存在。符合预期的是，仿真中的分布内（in-distribution）评估超过了真实环境表现。有趣的是，当同时对仿真与真实数据进行微调时，性能提升超出了比例——尽管训练集中只有 10 个真实回合。

我们在 143 个真实回合与 500 个仿真回合的混合上也观察到了这一效应。如图 7 右侧所示，模型在训练 10000 步后已达到了完美的成功率。此外，仿真性能更接近真实性能——这是因为评估域是分布内的。仿真成功率较低可由任务的更高难度解释：为使接触仿真有效，长方体必须在接近中心处被抓取；而在真实实验中，靠近边沿的抓取常常也能成功。

### IV-E RL 训练流水线

RL 与 VLA 训练流水线的需求差别很大。VLA 训练通常受 GPU 限制，遵循一个标准的深度学习流程——在数据集上训练一个大型神经网络。相比之下，RL 训练涉及仿真与策略推理之间的紧密交互循环。虽然最近的基于 GPU 的仿真器借助大规模并行能显著提高吞吐，但基于视觉的策略及相关的渲染开销仍占总计算成本的相当一部分。因此，基于 CPU 的 MuJoCo 仿真在性能与广泛可用性之间是一个不错的折衷。本实验展示 RCS 如何迎合 RL 流水线的需求：在图 5 所示的复刻 MuJoCo 场景中训练一个策略以解决 Pick-Cuboid。

RCS 原生支持并行化，并与 Stable Baselines 3（SB3）[21] 开箱即用地支持并行训练。其基于 Gymnasium 的 API 与绝大多数 Python RL 库兼容。当渲染一张低分辨率相机图像时，我们的训练流水线在扩展到 24 路并行环境时能跑超过 2000 步/秒。注意，运行开销的很大一部分来自渲染，这可以通过简化场景大幅降低。这说明 RCS 不是 RL 训练流水线的瓶颈：性能依赖 MuJoCo 模型与 RL 算法自身的实现。

我们使用 ManiSkill 3 的 PickCube-v1 奖励函数进行势能奖励塑形（potential-based reward shaping）[17]，并加入一个离散的"成功"奖励。该函数基于 RCS 可访问的信息——物体之间的距离以及长方体是否被抓住。利用该奖励，我们使用 SB3 训练了一个 vanilla PPO 策略，将两台 RGB 相机的图像与本体感知状态作为输入，输出相对关节角。我们既没有调整性能也没有调整超参数。在 Nvidia RTX 4080 与 12 核 CPU 上，该策略在三小时内（850 万环境步）学会了以 100% 成功率将长方体提升。这表明 RCS 面向机器人学的工具集能够支持 RL 环境的开发与奖励函数的设计。

## V 结论与未来工作

本文中，我们介绍了 RCS——一个为可扩展机器人学习设计的精益生态系统，能够与机器学习工作流无缝集成。不同于其他机器人学习框架，RCS 以最小的开销提供了完整的功能集，同时具备最大的灵活性与性能。我们的实验表明，RCS 让数据采集、评估和推理这些环节的实现，在不同种类的机器人以及在仿真环境中都变得简便。这使得我们能够在不同机器人上协作完成对所选 VLA 的广泛评估，并展示了加入仿真数据如何能够显著提升策略性能。

RCS 的首次发布仅仅是一个起点。我们计划提供 ROS 接口，并增加对双手操作与移动操作任务的支持。结合已经具备的触觉感知支持，这将使 RCS 成为面向仿人机器人研究的面向未来的生态系统。
