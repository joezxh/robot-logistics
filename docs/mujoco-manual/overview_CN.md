# 概览

## 简介

**MuJoCo** 是 **Mu** lti-**Jo** int dynamics with **Co** ntact（多关节接触动力学）的缩写。它是一个通用物理引擎，旨在促进机器人学、生物力学、图形与动画、机器学习，以及其他需要快速准确仿真铰接结构与所处环境交互的研究与开发。MuJoCo 最初由 Roboti LLC 开发，于 2021 年 10 月被 Google DeepMind 收购并[免费开放](https://github.com/google-deepmind/mujoco/blob/main/LICENSE)，并于 2022 年 5 月开源。MuJoCo 代码库可在 GitHub 上的 [google-deepmind/mujoco](https://github.com/google-deepmind/mujoco) 仓库获取。

MuJoCo 是一个带有 C API 的 C/C++ 库，面向研究人员和开发者。其运行时仿真模块经过调优以最大化性能，并运行在内置 XML 解析器和编译器预先分配的低级数据结构之上。用户使用原生 MJCF 场景描述语言定义模型——这是一种 XML 文件格式，旨在尽可能做到人类可读、可编辑。URDF 模型文件也可以被加载。该库包含由原生 GUI 提供、在 OpenGL 中渲染的交互式可视化功能。MuJoCo 还暴露了大量用于计算物理相关量的工具函数。

MuJoCo 可用于实现基于模型的计算，例如控制综合、状态估计、系统辨识、机构设计、通过逆动力学的分析，以及用于机器学习应用的并行采样。它也可以作为更传统的仿真器使用，包括用于游戏和交互式虚拟环境。

### 关键特性

MuJoCo 的功能特性清单很长。这里我们概述其中最为显著的几项。

广义坐标结合现代接触动力学

物理引擎传统上分为两类。机器人学和生物力学引擎在广义坐标或关节坐标下使用高效准确的递归算法。然而它们要么不包含接触动力学，要么依赖早期的弹簧-阻尼方法，这要求非常小的时间步长。游戏引擎则采用更现代的方法，通过求解一个优化问题来求得由摩擦接触产生的力。然而，它们常常退回到过度确定的笛卡尔表示，在这种表示中关节约束被数值地施加，当涉及复杂的运动学结构时会导致不准确和不稳定。MuJoCo 首创性地将广义坐标仿真与基于优化的接触动力学结合起来。这种方法后来被其他仿真器所采用。习惯于游戏引擎的用户一开始可能会觉得广义坐标反直觉；请参阅下文[澄清](overview_CN.md#clarifications)一节。

柔性、凸且可解析求逆的接触动力学

在现代接触动力学方法中，由摩擦接触引起的力或冲量通常被定义为线性或非线性互补问题（LCP 或 NCP）的解，而这两者都是 NP 难问题。MuJoCo 基于一种不同的接触物理学表述，可归约为一个凸优化问题，详见[计算](computation/index_CN.md)一章。我们的模型允许柔性接触和其他约束，并具有唯一确定的逆，便于数据分析和控制应用。默认的牛顿求解器提供二次收敛；备选算法还包括共轭梯度法和可处理椭圆摩擦锥的广义投影 Gauss-Seidel 方法。该求解器对摩擦接触（包括扭转摩擦和滚动摩擦）、无摩擦接触、关节与肌腱限位、关节与肌腱中的干摩擦，以及多种等式约束提供了统一的处理。

肌腱几何

MuJoCo 可以对肌腱的三维几何进行建模——肌腱是服从缠绕和途经点约束的最短路径字符串。其机制类似于 OpenSim，但实现了更受限、闭式的一组缠绕选项以加速计算。它还提供机器人学特有的结构，如滑轮和耦合自由度。肌腱既可用于驱动，也可用于对肌腱长度施加不等式或等式约束。

通用驱动模型

在使用与模型无关的 API 的同时，设计一个足够丰富的驱动模型是颇具挑战的。MuJoCo 通过采用一种抽象驱动模型来实现这一目标，该模型可以具有不同类型的传动、力生成和内部动力学（即使得整体动力学变为三阶的状态变量）。这些组件可以被实例化，从而以统一的方式建模电机、气动和液压缸、PD 控制器、生物肌肉以及许多其他执行器。

可重构计算流水线

MuJoCo 有一个顶层步进函数 [mj_step](APIreference/APIfunctions_CN.md#mj-step)，它运行整个前向动力学并推进仿真的状态。然而，在仿真之外的许多应用中，能够运行计算流水线的选定部分是有益的。为此，MuJoCo 提供了大量的[标志](XMLreference_CN.md#option-flag)，它们可以以任意组合设置，使用户能够根据需要重新配置流水线，而不仅仅是通过[选项](XMLreference_CN.md#option)选择算法和算法参数。此外，许多底层函数也可以直接调用。用户自定义的回调可以实现自定义的力场、执行器、碰撞例程和反馈控制器。

模型编译

如上所述，用户使用一种称为 MJCF 的 XML 文件格式定义 MuJoCo 模型。该模型随后由内置编译器编译成低级数据结构 [mjModel](APIreference/APItypes_CN.md#mjmodel)，该结构被交叉索引并针对运行时计算进行了优化。编译后的模型也可以保存为二进制 MJB 文件。

模型与数据分离

MuJoCo 在运行时将仿真参数分离为两个数据结构（C 结构体）：

  * [mjModel](APIreference/APItypes_CN.md#mjmodel) 包含模型描述，预期保持不变。其中嵌入了其他一些包含仿真与可视化选项的结构，这些选项偶尔需要更改，但这由用户来完成。

  * [mjData](APIreference/APItypes_CN.md#mjdata) 包含所有动态变量和中间结果。它被用作一个便签簿（scratch pad），所有函数都从中读取输入并写入输出——这些输出随后又成为仿真流水线后续阶段的输入。它还包含一个预先分配并由内部管理的栈，因此在模型初始化之后运行时模块无需再调用内存分配函数。

[mjModel](APIreference/APItypes_CN.md#mjmodel) 由编译器构建。[mjData](APIreference/APItypes_CN.md#mjdata) 在运行时给定 [mjModel](APIreference/APItypes_CN.md#mjmodel) 后被构建。这种分离使得可以轻松仿真多个模型，以及每个模型的多个状态和控制，进而促进用于采样的[多线程](programming/simulation_CN.md#simultithread)和[有限差分](APIreference/APIfunctions_CN.md#mjd-transitionfd)。顶层 API 函数反映了这种基本分离，其格式为：

    void mj_step(const mjModel* m, mjData* d);

性能

MuJoCo 的运行时在初始化之后执行零内存分配——所有工作内存都在 `mjData` 中预先分配。单个仿真步默认是单线程的，但[约束孤岛](computation/index_CN.md#soisland)使得在一个步内可以实现逐孤岛并行。大规模的数据并行采样通过创建多个共享同一个 `mjModel` 并在独立线程上运行的 `mjData` 实例来实现；参见[多线程](programming/simulation_CN.md#simultithread)。

交互式仿真与可视化

原生的[3D 可视化器](programming/visualization_CN.md#visualization)提供对网格和几何图元的渲染、纹理、反射、阴影、雾、透明度、线框、天空盒、立体可视化（在支持四缓冲 OpenGL 的显卡上）。该功能用于生成 3D 渲染，帮助用户洞察物理仿真，包括诸如自动生成的模型骨架、等效惯性盒、接触位置与法向、可分离为法向和切向分量的接触力、外部扰动、局部坐标系、关节与执行器轴，以及文本标签等可视化辅助。可视化器期望一个带有 OpenGL 渲染上下文的通用窗口，从而允许用户选用自己所偏好的 GUI 库。随 MuJoCo 分发的代码示例 [simulate.cc](programming/samples_CN.md#sasimulate) 展示了如何用 GLFW 库做到这一点。一个相关的易用特性是能够“伸入”仿真，推开物体并观察物理如何响应。用户选择外部力和力矩将施加到的刚体，并看到扰动的实时渲染及其动力学后果。这可用于以可视化方式调试模型、测试反馈控制器的响应，或将模型配置到期望的位姿。

强大而直观的建模语言

MuJoCo 拥有自己的建模语言 MJCF。MJCF 的目标是提供对 MuJoCo 全部计算能力的访问，同时使用户能够快速开发新模型并进行实验。这一目标在很大程度上得益于一个广泛的[默认设置](modeling_CN.md#cdefault)机制而得以实现，该机制类似于内联在 HTML 中的层叠样式表（CSS）。虽然 MJCF 有许多元素和属性，但用户在任何给定模型中需要设置的却少得惊人。这使得 MJCF 文件比其他许多格式更短、更具可读性。

复合柔性对象的自动生成

MuJoCo 的柔性约束可用于建模绳索、布料和可变形的三维物体。这需要一个由大量常规刚体、关节、肌腱和约束协同工作。该建模语言拥有高级宏，由模型编译器自动展开为所需的标准模型元素集合。重要的是，这些生成的柔性对象能够与仿真的其余部分充分交互。

约束孤岛与休眠

约束求解器会自动发现相互独立的[约束孤岛](computation/index_CN.md#soisland)——由约束耦合在一起、可独立求解的刚体分组。这使得逐孤岛并行成为可能，并避免了过度求解：每个孤岛以其所需的迭代次数收敛，而无约束的自由度则被完全跳过。此外，[孤岛休眠](computation/index_CN.md#sleeping) 可以冻结静止的孤岛，在场景的部分区域处于静止时大幅减少计算量。

插件系统

MuJoCo 支持[引擎插件](programming/extension_CN.md)，用自定义元素扩展物理引擎：传感器、执行器和被动力。插件是动态加载的共享库，它们向引擎注册自身，并按每个模型元素实例化。这允许在不修改核心引擎的情况下扩展 MuJoCo。

GPU 加速后端

除了 C 引擎之外，MuJoCo 还有用于大规模并行仿真的 GPU 加速后端：[MJX](mjx_CN.md)（JAX）和 [MuJoCo Warp](mjwarp/index_CN.md)（NVIDIA Warp）。这两个后端都消费相同的 `mjModel` 和 `mjData` 结构，允许在 CPU 和 GPU 之间无缝转移。一等公民的[Python 绑定](python_CN.md)提供了对完整 C API 的访问。

### 模型实例

MuJoCo 中有几个被称为“模型”的实体。用户用 MJCF 或 URDF 编写的 XML 文件定义模型。软件随后可以在不同介质（文件或内存）和不同描述层级（高层或低层）上创建同一模型的多个实例。如下表所示，所有组合都是可能的：

| 高层 | 低层
---|---|---
**文件** | MJCF/URDF（XML）、MJZ（Zip 归档） | MJB（二进制）
**内存** | [mjSpec](APIreference/APItypes_CN.md#mjspec)（C 结构体） | [mjModel](APIreference/APItypes_CN.md#mjmodel)（C 结构体）

所有运行时计算都使用 [mjModel](APIreference/APItypes_CN.md#mjmodel) 来执行，它过于复杂而无法手动创建。这就是为什么我们有两层建模。高层存在的目的是为用户提供便利：它唯一的用途就是被编译成一个可以执行计算的低层模型。生成的 [mjModel](APIreference/APItypes_CN.md#mjmodel) 可以被加载并保存到二进制文件（MJB）中，但那些文件是特定于版本的且无法反编译，因此模型应当始终以 XML 文件的形式维护，或打包进 MJZ 归档中。

[mjSpec](APIreference/APItypes_CN.md#mjspec) C 结构体与 MJCF 文件格式是一一对应的。XML 加载器解释 MJCF 或 URDF 文件，创建相应的 [mjSpec](APIreference/APItypes_CN.md#mjspec) 并将其编译为 [mjModel](APIreference/APItypes_CN.md#mjmodel)。用户可以以编程方式创建 [mjSpec](APIreference/APItypes_CN.md#mjspec)，然后将其保存为 MJCF/MJZ，或者编译它。程序化的模型创建与编辑在[模型编辑](programming/modeledit_CN.md)一章中描述。

下图展示了获取一个 [mjModel](APIreference/APItypes_CN.md#mjmodel) 的不同路径：

  * （文本编辑器）→ MJCF/URDF 文件 →（MuJoCo 解析器 → mjSpec → 编译器）→ mjModel

  * MJZ 归档 →（MJZ 解码器 → mjSpec → 编译器）→ mjModel

  * （用户代码）→ mjSpec →（MuJoCo 编译器）→ mjModel

  * MJB 文件 →（模型加载器）→ mjModel

模型和 spec 也可以使用 [mj_encode](APIreference/APIfunctions_CN.md#mj-encode) 序列化或打包回磁盘。

### 示例

下面是一个用 MuJoCo 的 MJCF 格式编写的简单模型。它定义了一个固定在世界上、用于更好照亮物体并投射阴影的平面，以及一个具有 6 自由度的漂浮盒子（这正是“free”关节的作用）。

[hello.xml](https://mujoco.readthedocs.io/en/stable/_static/hello.xml)：

    <mujoco>
      <worldbody>
        <light diffuse=".5 .5 .5" pos="0 0 3" dir="0 0 -1"/>
        <geom type="plane" size="1 1 0.1" rgba=".9 0 0 1"/>
        <body pos="0 0 1">
          <joint type="free"/>
          <geom type="box" size=".1 .2 .3" rgba="0 .9 0 1"/>
        </body>
      </worldbody>
    </mujoco>

内置的 OpenGL 可视化器将此模型渲染为：

[![_images/hello.png](https://mujoco.readthedocs.io/en/stable/images/hello.png) ](https://mujoco.readthedocs.io/en/stable/_images/hello.png)

如果对该模型进行仿真，盒子将落在地面上。下面给出了用于被动动力学、不含渲染的基础仿真代码。

    #include "mujoco.h"
    #include "stdio.h"

    char error[1000];
    mjModel* m;
    mjData* d;

    int main(void) {
      // 从文件加载模型并检查错误
      m = mj_loadXML("hello.xml", NULL, error, 1000);
      if (!m) {
        printf("%s\n", error);
        return 1;
      }

      // 创建与模型对应的 data
      d = mj_makeData(m);

      // 仿真运行 10 秒
      while (d->time < 10)
        mj_step(m, d);

      // 释放模型和数据
      mj_deleteData(d);
      mj_deleteModel(m);

      return 0;
    }

从技术上讲这是一个 C 文件，但它同样是一个合法的 C++ 文件。事实上 MuJoCo 的 API 同时兼容 C 和 C++。通常用户代码会用 C++ 编写，因为这样更方便，而且不会牺牲效率，因为计算瓶颈在于已经高度优化的仿真器内部。

函数 [mj_step](APIreference/APIfunctions_CN.md#mj-step) 是顶层函数，它将仿真状态推进一个时间步。当然，这个例子只是一个被动动力系统。当用户指定控制或施加力并开始与系统交互时，事情就变得更有趣了。

接下来我们提供一个更详尽的示例，展示 MJCF 的若干特性。考虑下面的 [example.xml](https://mujoco.readthedocs.io/en/stable/_static/example.xml)：

    <mujoco model="example">
      <default>
        <geom rgba=".8 .6 .4 1"/>
      </default>

      <asset>
        <texture type="skybox" builtin="gradient" rgb1="1 1 1" rgb2=".6 .8 1" width="256" height="256"/>
      </asset>

      <worldbody>
        <light pos="0 1 1" dir="0 -1 -1" diffuse="1 1 1"/>
        <body pos="0 0 1">
          <joint type="ball"/>
          <geom type="capsule" size="0.06" fromto="0 0 0  0 0 -.4"/>
          <body pos="0 0 -0.4">
            <joint axis="0 1 0"/>
            <joint axis="1 0 0"/>
            <geom type="capsule" size="0.04" fromto="0 0 0  .3 0 0"/>
            <body pos=".3 0 0">
              <joint axis="0 1 0"/>
              <joint axis="0 0 1"/>
              <geom pos=".1 0 0" size="0.1 0.08 0.02" type="ellipsoid"/>
              <site name="end1" pos="0.2 0 0" size="0.01"/>
            </body>
          </body>
        </body>

        <body pos="0.3 0 0.1">
          <joint type="free"/>
          <geom size="0.07 0.1" type="cylinder"/>
          <site name="end2" pos="0 0 0.1" size="0.01"/>
        </body>
      </worldbody>

      <tendon>
        <spatial limited="true" range="0 0.6" width="0.005">
          <site site="end1"/>
          <site site="end2"/>
        </spatial>
      </tendon>
    </mujoco>

这个模型是一个 7 自由度机械臂，“握着”一根另一端连有圆柱体的绳子。绳子被实现为具有长度限制的肌腱。肩部是一个球关节，肘部和腕部是一对铰链关节。圆柱体内部的盒子表示一个自由“关节”。XML 中最外层的 body 元素是必要的 worldbody。注意，在两个刚体之间使用多个关节并不需要创建哑（dummy）刚体。

MJCF 文件包含指定该模型所需的最少信息。胶囊由空间中的线段定义——在这种情况下只需给出胶囊的半径即可。刚体坐标系的位置和朝向由属于它的 geoms 推断而来。惯性特性在均匀密度假设下由 geom 形状推断而来。两个 site 被命名，是因为肌腱定义需要引用它们，但其他任何元素都未命名。关节轴只为铰链关节而非球关节定义。碰撞规则自动定义。摩擦属性、重力、仿真时间步长等都被设为默认值。顶部指定的默认 geom 颜色应用于所有 geoms。

除了将编译后的模型保存为二进制的 MJB 格式外，我们还可以将其保存为 MJCF 或人类可读的文本；分别参见 [example_saved.xml](https://mujoco.readthedocs.io/en/stable/_static/example_saved.xml) 和 [example_saved.txt](https://mujoco.readthedocs.io/en/stable/_static/example_saved.txt)。XML 版本与原始版本相似，而文本版本包含来自 `mjModel` 的所有信息。将文本版本与 XML 版本进行比较，可以看出模型编译器为我们做了多少工作。

## 模型元素

本节简要描述可以包含在 MuJoCo 模型中的所有元素。稍后我们会更详细地解释底层的计算、在 MJCF 中指定元素的方式，以及它们在 `mjModel` 中的表示。

### 选项

每个模型都有下面列出的三组选项。它们总是被包含在内。如果在 XML 文件中没有指定它们的值，则使用默认值。这些选项的设计使得用户可以在每个仿真时间步之前更改它们的值。然而在一个时间步之内，不应更改任何选项。

#### `mjOption`

此结构包含所有影响物理仿真的选项。它用于选择算法并设置其参数、启用和禁用仿真流水线的不同部分，以及调整重力等系统级物理属性。

#### `mjVisual`

此结构包含所有可视化选项。还有额外的 OpenGL 渲染选项，但它们是依赖于会话的，不属于模型的一部分。

#### `mjStatistic`

此结构包含由编译器计算得到的关于模型的统计信息：刚体的平均质量、模型的空间范围等。它仅用于提供参考信息，也因为可视化器使用它来进行自动缩放。

### 资产

资产本身并不是模型元素。模型元素可以引用它们，在这种情况下资产会以某种方式改变引用元素的性质。一个资产可以被多个模型元素引用。由于包含资产的唯一目的是引用它，而引用只能通过名称进行，因此每个资产都有一个名称（在适用时可以从文件名推断）。相反，常规元素的名称可以留空。

#### 网格（Mesh）

MuJoCo 可以从 OBJ 文件和二进制 STL 加载三角化网格。可以使用 [MeshLab](https://www.meshlab.net/) 等软件从其他格式转换。虽然任何三角形集合都可以作为网格加载和可视化，但碰撞检测器针对的是凸包工作。在编译期有用于缩放网格以及为其拟合一个基本几何形状的选项。网格也可用于自动推断惯性特性——方法是将其视为三角金字塔的并集，并合并它们的质量和惯性。注意网格没有颜色，相反，网格使用引用它的 geom 的材质属性来着色。相比之下，所有空间特性都由网格数据决定。MuJoCo 同时支持 OBJ 以及一种用于法向和纹理坐标的自定义二进制文件格式。网格也可以直接内嵌在 XML 中。

#### 蒙皮（Skin）

蒙皮网格（skin）是其形状可以在运行时变形的网格。它们的顶点附着到刚体（在此上下文中称为“骨骼/bone”）上，每个顶点可以属于多个骨骼，从而产生平滑的蒙皮变形。蒙皮是纯可视化的对象，不影响物理，但尽管如此它们可以显著提升视觉真实感。蒙皮可以从自定义二进制文件加载，或像网格一样直接内嵌在 XML 中。当自动生成复合柔性对象时，模型编译器也会为这些对象生成蒙皮。

#### 高度场（Height field）

高度场可以从 PNG 文件（内部转换为灰度）加载，或从稍后描述的自定义二进制格式文件加载。高度场是一个高程数据的矩形网格。编译器将数据归一化到 [0-1] 范围。高度场的实际空间范围随后由引用它的 geom 的 size 参数决定。高度场只能从附着到世界 body 的 geoms 中引用。出于渲染和碰撞检测的目的，网格矩形被自动三角化，因此高度场被视为三角柱的并集。与这样一个复合对象的碰撞原则上可以为单个 geom 对生成大量接触点。如果发生了这种情况，只会保留前 64 个接触点。其理由是，高度场应当用于建模地形图，其空间特征相对于仿真中的其他对象较大，因此对于设计良好的模型，接触点数量会很少。

#### 纹理（Texture）

纹理可以从 PNG 或 KTX 文件加载，或由编译器基于用户定义的程序化参数合成。还有一个选项是在模型创建时留空纹理，并在运行时稍后更改——以便在 MuJoCo 仿真中渲染视频，或创建其他动态效果。可视化器支持两种类型的纹理映射：2D 和立方体。2D 映射对平面和高度场很有用。立方体映射对于将纹理“收缩包裹”在三维对象周围而无需指定纹理坐标很有用。它也用于创建天空盒。立方体映射的六个面可以从单独的图像文件、一个合成图像文件加载，或通过重复同一图像来生成。与所有其他直接从模型元素引用的资产不同，纹理只能从另一个资产（即材质）引用，而该资产再从模型元素引用。

#### 材质（Material）

材质用于控制 geoms、sites 和 tendons 的外观。这是通过从相应的模型元素引用该材质来实现的。外观包括纹理映射，以及与下方 OpenGL 光源交互的其他属性：RGBA、镜面反射率、光泽度、自发光。材质也可用于使对象具有反射性。目前反射仅在平面和盒子的 Z+ 面上渲染。注意，模型元素也可以有自己的局部 RGBA 参数来设置颜色。如果同时指定了材质和局部 RGBA，则局部定义优先。

### 运动学树

MuJoCo 仿真一组刚体的动力学，这些刚体的运动通常受到约束。系统状态用关节坐标表示，刚体被显式地组织成运动学树。树结构由 `mjModel.body_parentid` 给出，这是一个长度为 `nbody >= 1` 的整型数组。顶层的“世界”body 总是存在（id 为 `0`）且是它自身的父级，因此 `body_parentid[0] == 0`，且对于所有其他 `i` 有 `body_parentid[i] < i`。注意，世界 body 和其他静态（无关节）的子 body 构成了一个唯一的“静态树”，没有关联的自由度。在这个顶层静态树之下，可以附着多个运动学树，见下文的[树](overview_CN.md#elemtree)。

不允许运动学环；如果需要环关节，应当用等式约束来建模。因此 MuJoCo 模型的骨干是一个或多个由嵌套 body 定义形成的运动学树；一个孤立的漂浮 body 算作一棵树。下面列出的其他几个元素在 body 内部定义并属于该 body。这与稍后列出的独立元素形成对比，后者不能关联到单个 body。

#### 刚体（Body）

刚体具有质量和惯性特性，但没有任何几何特性。相反，几何形状（或 geoms）附着到刚体上。每个 body 有两个坐标系：用于定义它以及相对于它定位其他元素的坐标系，以及一个以刚体质心为中心、与其主惯性轴对齐的惯性坐标系。该 body 的惯性矩阵在此坐标系中因此是对角的。在每个时间步，MuJoCo 递归地计算前向运动学，得到所有 body 在全局笛卡尔坐标中的位置和朝向。这为所有后续计算提供了基础。刚体数量由 `mjModel.nbody` 给出。

#### 关节（Joint）

关节在 body 内部定义。它们在 body 与其父级之间创建运动自由度（DOF）。在没有关节的情况下，body 被焊接到其父级。这与游戏引擎相反，后者使用过度完备的笛卡尔坐标，其中关节是移除而非添加自由度。有四种类型的关节：球关节、滑动关节、铰链关节，以及创建漂浮 body 的“自由关节”。一个 body 可以有多个关节。通过这种方式，复合关节被自动创建，而无需定义哑 body。球关节和自由关节的朝向分量用单位四元数表示，MuJoCo 中的所有计算都尊重四元数的性质。关节数量由 `mjModel.njnt` 给出。

##### 关节参考（Joint reference）

参考位姿是存储在 `mjModel.qpos0` 中的一组关节位置向量。它对应于模型处于其初始构型时关节的数值。在我们之前的例子中，肘部被创建为 90° 角的弯曲构型。但 MuJoCo 不知道什么是肘部，因此默认将此关节构型视为数值 0。我们可以通过 [joint](XMLreference_CN.md#body-joint) 的 ref 属性来覆盖默认行为，并指定初始构型对应于 90°。所有关节的参考值被汇编进向量 `mjModel.qpos0`。每当仿真被重置时，关节构型 `mjData.qpos` 被设为 `mjModel.qpos0`。在运行时，关节位置向量被解释为相对于参考位姿。特别是，由关节施加的空间变换量是 `mjData.qpos - mjModel.qpos0`。这个变换是附加在存储在 `mjModel` 的 body 元素中的父子平移和旋转偏移之上的。ref 属性只适用于标量关节（滑动和铰链）。对于球关节，保存在 `mjModel.qpos0` 中的四元数始终是 (1,0,0,0)，对应于零旋转。对于自由关节，漂浮 body 的全局三维位置和四元数保存在 `mjModel.qpos0` 中。

##### 弹簧参考（Spring reference）

这是所有关节和肌腱弹簧达到其自然长度时的位姿。当关节构型偏离弹簧参考位姿时，会生成弹簧力，并且该力与偏离量成线性比例。弹簧参考位姿保存在 `mjModel.qpos_spring` 中。对于滑动和铰链关节，弹簧参考用属性 springref 指定。对于球关节和自由关节，弹簧参考对应于初始模型构型。

#### 自由度（DOF）

自由度与关节密切相关，但不是一一对应的，因为球关节和自由关节有多个自由度。可以将关节视为指定位置信息，而将自由度视为指定速度和力信息。更正式地说，关节位置是系统构型流形上的坐标，而关节速度是该流形在当前位置处切空间上的坐标。自由度具有与速度相关的属性，如摩擦损失、阻尼、电枢惯性。所有作用在系统上的广义力都在自由度的空间中表达。相比之下，关节具有与位置相关的属性，如限位和弹簧刚度。自由度不是由用户直接指定的。相反，它们是编译器根据关节创建的。自由度数量由 `mjModel.nv` 给出。

#### 树（Tree）

如[上文](overview_CN.md#kinematic)所述，运动中的刚体被组织成运动学树。一棵运动学树或“树”是指 _一个可运动的 body 及其所有后代_。因此，世界和其他静态 body 处于全局树结构中，但不关联于任何 _树_。由于全局树结构使用深度优先组织，属于单棵树的所有 body、关节和自由度总是连续的。注意，与（如果是静态的）不关联于任何树的 body 不同，关节和自由度总是关联于一棵树。无论是[孤岛发现](computation/index_CN.md#soisland)还是[孤岛休眠](computation/index_CN.md#sleeping)都在树的层级上操作。

树的数量由 `mjModel.ntree` 给出。例如，一个包含三个自由 body 和[标准类人模型](https://github.com/google-deepmind/mujoco/blob/main/model/humanoid/humanoid.xml)的模型有 `ntree = 4`。注意，虽然树确实是全局树（其根是世界）的子树，但这不应与特定术语 `subtree` 混淆，后者保留用于每个 body 的局部树，因此 `mjModel.body_subtreemass` 给出每个 body 下方局部树的总质量，对所有 body 都如此。

#### 几何体（Geom）

Geoms 是刚性附着到 body 上的三维形状。多个 geoms 可以附着到同一个 body。这一点在 MuJoCo 只支持凸 geom-geom 碰撞，而创建非凸对象的唯一方式是将它们表示为凸 geoms 的并集这一事实下尤为有用。除了碰撞检测和后续接触力的计算外，geoms 还用于渲染，以及在省略 body 质量和惯性时自动推断它们。MuJoCo 支持几种基本几何形状：平面、球、胶囊、椭球、圆柱、盒子。一个 geom 也可以是一个网格或高度场；这是通过引用相应的资产来实现的。Geoms 有许多影响仿真和可视化的材质属性。geom 数量由 `mjModel.ngeom` 给出。

#### 站点（Site）

Sites 本质上是轻量级的 geoms。它们表示 body 坐标系内感兴趣的位置。Sites 不参与碰撞检测或惯性特性的自动计算，但它们可用于指定其他对象的空间特性，如传感器、肌腱路由和曲柄滑块端点。site 数量由 `mjModel.nsite` 给出。

#### 相机（Camera）

一个模型中可以定义多个相机。总有一个默认相机，用户可以在交互式可视化器中用鼠标自由移动。然而，定义额外的相机通常很方便，这些相机要么固定到世界上，要么附着到某个 body 上并随其移动。除了相机的位置和朝向，用户还可以调整用于立体渲染的垂直视场角和瞳孔间距，以及创建立体虚拟环境所需的斜投影。在建模具有不完美光学的真实相机时，可以分别为水平和垂直方向指定不同的焦距以及非中心的主点。相机数量由 `mjModel.ncam` 给出。

#### 光源（Light）

光源可以固定到世界 body 或附着到运动中的 body。可视化器提供对 OpenGL（固定功能）中完整光照模型的访问，包括环境光、漫反射和镜面反射分量、衰减和截止、位置光和方向光、雾。光源，或更准确地说被它们照亮的物体，也可以投射阴影。然而，与材质反射类似，每个投射阴影的光源都会增加一次渲染遍，因此应谨慎使用此特性。详细记录光照模型超出了本章范围；请参见 [OpenGL 文档](http://www.glprogramming.com/red/chapter05.html)。注意，除了用户在运动学树中定义的光源外，还有一个随相机移动、默认的头灯。其属性通过 mjVisual 选项调整。光源数量由 `mjModel.nlight` 给出。

### 独立元素

这里我们描述那些不属于单个 body、因此在运动学树之外描述的模型元素。

#### 肌腱（Tendon）

肌腱是标量长度元素，可用于驱动、施加限位和等式约束，或创建弹簧-阻尼器和摩擦损失。肌腱有两种类型：固定肌腱和空间肌腱。固定肌腱是（标量）关节位置的线性组合。它们对建模机械耦合很有用。空间肌腱被定义为穿过一系列指定 site（或途经点）序列、或缠绕在指定 geoms 周围的最短路径。只支持球体和圆柱作为缠绕 geom，并且圆柱在缠绕时被视为具有无限长度。为了避免肌腱从缠绕 geom 的一侧突然跳到另一侧，用户也可以指定偏好的一侧。如果肌腱路径中有多个缠绕 geom，它们必须由 site 分隔，以避免需要迭代求解器。空间肌腱也可以使用滑轮拆分为多个分支。

#### 执行器（Actuator）

MuJoCo 提供了一个灵活的驱动模型，其三个组件可以独立指定。它们共同决定了执行器的工作方式。通过协调地指定这些组件，可以得到常见的执行器类型。这三个组件是传动、激活动力学和力生成。传动指定执行器如何附着到系统的其余部分；可用类型有 joint、tendon、slider-crank、site 和 body。激活动力学可用于建模气动或液压缸的内部激活状态以及生物肌肉；使用此类执行器使整体系统动力学变为三阶。力生成机制决定了提供给执行器作为输入的标量控制信号如何被映射为一个标量力，该力随后又通过由传动推断出的力臂被映射为一个广义力。

#### 传感器（Sensor）

MuJoCo 可以生成模拟传感器数据，保存在全局数组 `mjData.sensordata` 中。该结果不用于任何内部计算；相反，它之所以被提供，是因为用户大概需要它来进行自定义计算或数据分析。可用的传感器类型包括触摸传感器、惯性测量单元（IMU）、力-力矩传感器、关节和肌腱位置与速度传感器、执行器传感器、body 坐标系传感器、测距仪，以及许多其他类型；完整列表见 XML 参考的 [Sensor](XMLreference_CN.md#sensor) 一节。还有一种用户传感器类型，允许用户代码将任何其他感兴趣的量插入到传感器数据数组中。MuJoCo 还具有离屏渲染能力，使得模拟彩色和深度相机传感器变得简单。这不包含在标准传感器模型中，而必须通过编程方式完成，如代码示例 [simulate.cc](programming/samples_CN.md#sasimulate) 所示。

#### 等式（Equality）

等式约束可以施加超出运动学树结构及其内部定义的关节/自由度所施加的约束之外的额外约束。它们可用于创建环关节，或一般地建模机械耦合。执行这些约束的内部力与所有其他约束力量一起计算。可用的等式约束类型有：在一点处连接两个 body（在运动学树之外创建一个球关节）；将两个 body 焊接在一起；固定一个关节或肌腱的位置；通过三次多项式耦合两个关节或两个肌腱的位置；将 flex（即可变形网格）的边约束为其初始长度。

#### 柔性体（Flex）

Flex 表示可变形网格，可以是 1、2 或 3 维（因此其元素是胶囊、三角形或四面体）。与刚性附着到单个 body 的静态形状 geoms 不同，flex 的元素是可变形的：它们通过连接多个 body 构建，因此 body 的位置和朝向决定了运行时 flex 元素的形状。这些可变形元素支持碰撞和接触力，并生成被动力和约束力，从而柔性地保持可变形实体的形状。自动化功能可用于从文件加载网格、构建对应于网格顶点的 body、构建对应于网格面（或线或四面体，取决于维度）的 flex 元素，并获得相应的可变形网格。

#### 接触对（Contact pair）

MuJoCo 中的接触生成是一个精细的过程。被检查接触的 geom 对可以来自两个来源：统称为“动态”的自动邻近测试和其他过滤器，以及模型中提供的显式 geom 对列表。后者是一种独立的模型元素类型。因为接触涉及两个 geom 的组合，显式指定允许用户以动态机制无法做到的方式定义接触参数。它也对微调接触模型很有用，特别是添加那些被激进过滤方案移除的接触对。接触机制现已扩展到 flex 元素，它可以创建涉及两个以上 body 的接触交互。然而这类碰撞是自动化的，无法用接触对来微调。

#### 接触排除（Contact exclude）

这是接触对的相反操作：它指定应当被排除在候选接触对生成之外的 body 对（而非 geom 对）。它对于禁用那些由于几何原因导致不期望的永久接触的 body 之间的接触很有用。注意 MuJoCo 还有其他机制来处理这种情况（特别是如果 geoms 属于同一个 body 或父子 body，它们就不能碰撞），但有时这些自动化机制并不够，显式排除就变得必要。

#### 自定义数值（Custom numeric）

在 MuJoCo 仿真中输入自定义数值有三种方式。首先，可以在 XML 中定义全局数值字段。它们有一个名称和一组实数值数组。其次，某些模型元素的定义可以用元素特定的自定义数组来扩展。这是通过在 XML 元素 `size` 中设置属性 `nuser_XXX` 来实现的。第三，还有一个数组 `mjData.userdata`，它不被任何 MuJoCo 计算使用。用户可以在其中存储自定义计算的结果；回想一下，所有随时间变化的内容都应存储在 `mjData` 中，而不是 `mjModel` 中。

#### 自定义文本（Custom text）

自定义文本字段可以保存在模型中。它们可用于自定义计算——既是指定关键字命令，也是提供其他文本信息。不过不要用它们来写注释；将注释保存在编译后的模型中没有好处。XML 有自己的注释机制（被 MuJoCo 的解析器和编译器忽略），它更合适。

#### 自定义元组（Custom tuple）

自定义元组是 MuJoCo 模型元素的列表，可能包含其他元组。它们不被仿真器使用，但可用于为需要用户代码的元素组指定。例如，可以使用元组来定义用于自定义接触处理的 body 对。

#### 关键帧（Keyframe）

关键帧是仿真状态变量的快照。它包含关节位置、关节速度、执行器激活、控制、mocap body 位姿，以及仿真时间。模型中可以包含一个关键帧库。它们对于将系统状态重置到一个感兴趣的点很有用。注意，关键帧并不打算用于在模型中存储轨迹数据；此目的应使用外部文件。

读者很可能拥有其他物理仿真器及相关约定的经验，以及一些与 MuJoCo 不一致的一般编程实践。这有可能造成混淆。本节的目标是预先澄清最可能引起混淆的方面；它介于 FAQ 和针对选定主题的教程之间。我们需要引用文档后面覆盖的内容，但尽管如此，下面的文字仍是尽可能自包含和入门性的。

### 发散（Divergence）

仿真的发散发生在状态元素迅速趋向无穷大时。在 MuJoCo 中这通常表现为 [mjWARN_BADQACC](APIreference/APItypes_CN.md#mjtwarning) 警告。发散在所有物理仿真中都普遍存在，不一定表明模型不好或仿真器有 bug，而更像是提示：对于给定的积分器选择，时间步长太大了。在物理仿真中，速度（大时间步）和稳定性（小时间步）之间总是存在张力。一个为速度调优得很好的模型具有不会导致发散的最大可能时间步长，这通常意味着它在极端条件下 _可能_ 会被诱发发散。从这个意义上说， _罕见_ 的发散情况实际上可能表明模型调优得很好。在所有情况下，都应当可以通过减小时间步长和/或切换到更稳定的[积分器](computation/index_CN.md#geintegration)来防止发散。如果那样仍失败，则是别的原因。例如，在 body 被初始化为相互穿透的模型中，巨大的排斥力可能将它们推开并导致发散。

### 单位未指定

MuJoCo 不指定基本的物理单位。用户可以按自己的选择来解释单位制，只要它是一致的。要理解这一点，考虑一个例子：一艘长 1 米、重 1 千克、有 1 牛顿推进器的飞船的动力学，与一艘长 1 厘米、重 1 克、有 1 达因推进器的飞船的动力学是相同的。这是因为 [MKS](https://en.wikipedia.org/wiki/MKS_system_of_units) 和 [CGS](https://en.wikipedia.org/wiki/Centimetre%E2%80%93gram%E2%80%93second_system_of_units) 都是一致的单位系统。这个属性允许用户按自己的选择缩放模型，这在仿真非常微小或非常巨大的事物时很有用，可以改善仿真的数值特性。

也就是说，鼓励用户使用 MKS，因为 MuJoCo 在两个地方使用了类 MKS 的默认值：

  * [gravity](XMLreference_CN.md#option) 的默认值是 (0, 0, -9.81)，对应于 MKS 下的地球表面重力。注意这并不真正指定 MKS 单位制，因为我们可能在 [Enceladus](https://en.wikipedia.org/wiki/Enceladus) 上使用 CGS。

  * [geom 密度](XMLreference_CN.md#body-geom)（用于推断 body 质量和惯性）的默认值是 1000，对应于 MKS 下水的密度。

一旦选定了一致的基本单位系统（长度、质量、时间），所有导出单位都对应于该系统，如[量纲分析](https://en.wikipedia.org/wiki/Dimensional_analysis)中那样。例如，如果我们的模型被解释为 MKS，那么力和力矩分别以牛顿和牛顿·米为单位。

**角度：** 虽然在 MJCF 中角度可以用度来指定（实际上度是[默认值](XMLreference_CN.md#compiler)），但所有角向量 [mjModel](APIreference/APItypes_CN.md#mjmodel) 和 [mjData](APIreference/APItypes_CN.md#mjdata) 都以[弧度](https://en.wikipedia.org/wiki/Radian)表示。因此，例如，如果我们使用 MKS，[陀螺仪](XMLreference_CN.md#sensor-gyro) 报告的角速度单位为 rad/s，而铰链关节的刚度单位为 Nm/rad。

### 令人惊讶的碰撞

MuJoCo 默认排除属于具有直接父子关系的 body 对的 geoms 之间的碰撞。例如，考虑上文[示例](overview_CN.md#examples)一节中的机械臂模型：即使在胶囊 geoms 相互穿透的情况下，“肘部”也没有碰撞，因为前臂是上臂的直接子级。

然而，如果父级是静态 body，即世界 body，或相对于世界 body 没有任何自由度的 body，这种排除 **不适用**。这一行为记录在[碰撞检测](computation/index_CN.md#collision)一节中，用于防止物体穿过地面或穿过墙壁。然而，这一行为常常导致如下情况：

用户注释掉漂浮基座模型的 root 关节，也许是为了防止它掉落；现在由于基座 body 被算作静态的，出现了以前没有的新碰撞，用户感到困惑。有三种简单的方法可以避免这个问题：

  1. 使新变为静态的 body 成为一个 [mocap body](XMLreference_CN.md#body-mocap)。Mocap body 出于碰撞过滤的目的是其自身 body 组的根，而不是被焊接到世界上，因此其父子排除照常适用于它的子级。作为额外好处，该 body 可以被交互式地移动。

  2. 不要移除 root 关节。也许只需[禁用重力](XMLreference_CN.md#option-flag) 并可能添加一些[流体黏度](XMLreference_CN.md#option) 就足以防止你的模型移动过多。

  3. 使用[碰撞过滤](computation/index_CN.md#collision) 显式禁用不需要的碰撞，要么通过设置相关的 contype 和 conaffinity 属性，要么使用一个接触 [exclude](XMLreference_CN.md#contact-exclude) 指令。

### 面向数据的设计

MuJoCo 使用的是面向数据的架构，而非面向对象的架构。这里自然语义实体是整个物理仿真器，而不是具有私有状态和方法的单个对象。我们没有对象，而是有少量数据结构和大量在这些结构上操作的函数。

我们将模型（`mjModel`）与数据（`mjData`）分离。两者都是数据结构。模型包含描述所建模物理系统恒定特性所需的一切，而数据包含随时间变化的状态以及内部计算可复用的中间结果。所有顶层函数都期望将指向 `mjModel` 和 `mjData` 的指针作为参数。这种设计避免了全局变量，并自然地支持多线程：每个线程简单地操作它自己的 `mjData` 实例。

### 柔性与滑移

正如我们将在[计算](computation/index_CN.md)一章中详细解释的，MuJoCo 基于一种接触和其他约束的物理学的数学模型。这个模型本质上是柔性的，也就是说，对一个约束施加更大的力总是会导致更大的加速度，因此逆动力学可以被唯一地定义。这是可取的，因为它产生一个凸优化问题，并使得依赖逆动力学的分析成为可能，而且，我们在实践中需要建模的大多数接触都有某种柔性。然而，一旦我们允许柔性约束，我们实际上就是在创建一种新型动力学——即变形动力学——现在我们必须指定这些动力学如何表现。这需要精心设计的接触和其他约束的参数化，涉及可以逐约束设置的属性 solref 和 solimp，稍后将会描述。

这个柔性模型一个常常令人困惑的方面是，渐进的接触滑移无法避免。类似地，摩擦关节会在重力作用下逐渐屈服。这并不是因为求解器无法防止滑移（就达到摩擦锥或摩擦损失极限而言），而是因为它一开始就尝试去防止滑移。回想一下，对给定约束施加更大的力必须导致更大的加速度。如果要完全抑制滑移，这个关键性质就不得不被违反。因此，如果你在仿真中看到渐进滑移，直觉上的解释可能是摩擦不足，但在 MuJoCo 中很少是这种情况。相反，需要调整 `solref` 和 `solimp` 参数向量来减小这一效应。增大约束阻抗（solimp 的前两个元素）以及全局的 `mjModel.opt.impratio` 设置可能特别有效。这种调整通常需要更小的时间步长来保持仿真稳定，因为它们使得非线性动力学在数值上更难积分。滑移也会被通常更准确的牛顿求解器所减少。

对于希望完全抑制滑移的情况，有一个 [NoSlip](computation/index_CN.md#soalgorithms) 后处理求解器，它在主求解器之后运行。它通过忽略约束柔性来更新摩擦维度中的接触力。然而，当使用此选项时，MuJoCo 不再求解它本被设计来求解的凸优化问题，仿真可能变得不那么鲁棒。因此，使用牛顿求解器配合椭圆摩擦锥和较大的 `impratio` 值是减少滑移的推荐方式。更详细的建议，见建模一章中的[防止滑移](modeling_CN.md#cslippage)。

### 类型、名称、id

MuJoCo 支持大量模型元素，如前文总结。每种元素类型在 `mjModel` 中都有一个对应的节，列出其各种属性。例如关节限位数据在数组

    mjtNum* jnt_range;             // joint limits       (njnt x 2)

数组的大小（此处为 `njnt`）也由 `mjModel` 给出。第一个关节的限位首先被包含，然后是第二个关节的限位，依此类推。这种排序反映了 MuJoCo 中所有矩阵都采用行主序（row-major）格式这一事实。

可用的元素类型在 [mjtype.h](https://github.com/google-deepmind/mujoco/blob/main/include/mujoco/mjtype.h) 的枚举类型 [mjtObj](APIreference/APItypes_CN.md#mjtobj) 中定义。这些枚举大多在内部使用。一个例外是 MuJoCo API 中的函数 [mj_name2id](APIreference/APIfunctions_CN.md#mj-name2id) 和 [mj_id2name](APIreference/APIfunctions_CN.md#mj-id2name)，它们将元素名称映射到整数 id，反之亦然。这些函数以一个元素类型作为输入。

在 XML 中为模型元素命名是可选的。同一类型的两个元素（例如两个关节）不能同名。仅当某个给定元素需要在模型的其他地方被引用时才需要命名；在 XML 中的引用只能通过名称进行。一旦模型被编译，名称仍存储在 `mjModel` 中以便用户使用，尽管它们对仿真不再有进一步影响。名称对于查找对应的整数 id 以及渲染很有用：例如，如果你启用了关节标签，每个关节旁边都会显示一个字符串（未定义名称的元素被标记为“joint N”，其中 N 是 id）。

元素整数 id 对于索引 MuJoCo 数据数组至关重要。id 是 0 基的，遵循 C 约定。假设我们已经有了 `mjModel* m`。要打印名为“elbow”的关节的限位，执行：

    int jntid = mj_name2id(m, mjOBJ_JOINT, "elbow");
    if (jntid >= 0)
       printf("(%f, %f)\n", m->jnt_range[2*jntid], m->jnt_range[2*jntid+1]);

如果名称未找到，函数返回 -1，这就是为什么应当总是检查 id>=0。

### 刚体、几何体、站点

刚体、geoms 和 sites 是 MuJoCo 中大致对应于物理世界中刚体的元素。那么为什么它们是分开的？原因见此处所述的语义和计算两方面。

首先是相似之处。刚体、geoms 和 sites 都附着有空间坐标系（尽管刚体还有第二个坐标系，它以刚体质心为中心并与主惯性轴对齐）。这些坐标系的位置和朝向在每个时间步通过前向运动学从 `mjData.qpos` 计算出来。前向运动学的结果在 `mjData` 中以 bodies 的 xpos、xquat 和 xmat，geoms 的 geom_xpos 和 geom_xmat，sites 的 site_xpos 和 site_xmat 形式提供。

再是不同之处。刚体用于构建运动学树，并且是其他元素的容器，包括 geoms 和 sites。刚体具有空间坐标系、惯性特性，但没有与外观或碰撞几何相关的属性。这是因为此类属性不影响物理（当然接触除外，但接触是单独处理的）。如果你看过机器人学教科书中的运动学树图，刚体通常被画成不定形（amorphous）的形状——以说明它们的实际形状与物理无关。

Geoms（geometric primitive 的缩写）用于指定外观和碰撞几何。每个 geom 属于一个 body 并刚性附着到该 body。多个 geoms 可以附着到同一个 body。这一点在 MuJoCo 的碰撞检测器假设所有 geoms 都是凸的（如果网格不是凸的，它会在内部用其凸包替换）这一事实下尤为有用。因此，如果你想建模一个非凸形状，你必须将其分解为凸 geoms 的并集，并将它们全部附着到同一个 body。

一个 geom 也可以在 XML 中指定密度或质量值，模型编译器用它来计算父级 body 的质量和惯性。质量要么被指定，要么从 geom 的体积和[密度](XMLreference_CN.md#body-geom-density)计算。惯性由质量、形状和均匀密度假设计算。如果设置了 [shellinertia](XMLreference_CN.md#body-geom-shellinertia) 标志，则质量被假定均匀分布在 **表面** 上，密度被解释为面密度，对父级 body 的惯性贡献据此计算。在正在被仿真的实际 `mjModel` 中，geoms 没有惯性特性。

Sites 是轻量级的 geoms。它们具有相同的外观属性，但不能参与碰撞，也不能用于推断 body 质量。另一方面，sites 可以做 geoms 做不到的事情：它们可以指定触摸传感器的体积、IMU 传感器的附着、空间肌腱的路由、曲柄滑块执行器的端点。这些都是空间量，但它们并不对应于应当具有质量或与其他实体碰撞的实体——这正是 site 元素被创建的原因。Sites 也可用于指定用户感兴趣的点（或更准确地说坐标系）。

下面的例子说明了多个 sites 和 geoms 可以附着到同一个 body：本例中是两个 sites 和两个 geoms 附着到一个 body。

    <mujoco>
      <worldbody>
        <body pos="0 0 0">
          <geom type="sphere" size=".1" rgba=".9 .9 .1 1"/>
          <geom type="capsule" pos="0 0 .1" size=".05 .1" rgba=".9 .9 .1 1"/>
          <site type="box" pos="0 -.1 .3" size=".02 .02 .02" rgba=".9 .1 .9 1"/>
          <site type="ellipsoid" pos="0 .1 .3" size=".02 .03 .04" rgba=".9 .1 .9 1"/>
        </body>
      </worldbody>
    </mujoco>

### 关节坐标

MuJoCo 与游戏引擎之间的一个关键区别在于，MuJoCo 在广义或关节坐标下运行，而大多数游戏引擎在笛卡尔坐标下运行。这两种方法之间的差异可总结如下：

关节坐标：

  * 最适合诸如机器人之类的复杂运动学结构；

  * 关节 **添加** 默认会被焊接在一起的 body 之间的自由度；

  * 关节约束在表示中是隐式的，不会被违反；

  * 被仿真 body 的位置和朝向通过前向运动学从广义坐标获得，不能直接操纵（root body 除外）。

笛卡尔坐标：

  * 最适合许多相互弹开的 body，如分子动力学和盒子堆叠；

  * 关节 **移除** 默认会自由漂浮的 body 之间的自由度；

  * 关节约束被数值地强制执行，可能被违反；

  * 被仿真 body 的位置和朝向被显式表示并可直接操纵，尽管这可能引入进一步的关节约束违反。

关节坐标在处理同时属于一个模型、且模型中还包含运动学树的自由漂浮 body 时可能尤其令人困惑。这一点在下面澄清。

### 漂浮对象

在关节坐标下工作时，你不能简单地任意设置某个 body 的位置和朝向为你想要的值。要实现这种效果，你必须实现某种形式的逆运动学，它计算一组（不一定是唯一的）关节坐标，使前向运动学将 body 置于你想要它所在的位置。

对于漂浮 body，即通过一个自由关节连接到世界的 body，情况有所不同。此类 body 的位置和朝向以及线速度和角速度都在 `mjData.qpos` 和 `mjData.qvel` 中被显式表示，因此可以直接操纵。对于结构化的状态操作和序列化，见仿真一章的[状态与控制](programming/simulation_CN.md#sistatecontrol)。

自由关节的语义如下。位置数据是 7 个数（三维位置后跟单位四元数），而速度数据是 6 个数（三维线速度后跟三维角速度）。自由关节的线位置在全局坐标系中，线速度也是如此。自由关节的朝向（四元数）也在全局坐标系中。然而，自由关节的旋转速度在局部 body 坐标系中。这与其说是一个设计决定，不如说是对四元数拓扑的正确使用。角速度存在于四元数切空间中，该空间是为某个朝向局部定义的，因此坐标系局部的角速度是自然的参数化。加速度定义在与其对应速度相同的空间中。

自由关节总是在 body 坐标系中定义，然而在计算上将其与此 body 的惯性对齐是有利的。关于此选项的更多内容，见 [freejoint/align](XMLreference_CN.md#body-freejoint-align) 属性的文档。
